# 审查代码改动

确认仓库、审查范围及实际 base/head，区分提交内容、暂存内容和工作区改动；先读目标项目规则、相关架构、调用方与已有设计理由。远端基点改变后重新核对范围，不猜主分支名称。

优先发现会影响用户目标的缺陷：

- 沿真实入口追踪改动后的输入、默认值、输出和消费者，核对接口两侧的条件、错误、取消及兼容承诺。
- 涉及异步、进程或资源时，核对所有权、发布顺序、失败清理、重复完成和退出后的实际状态；按触及的路径检查，不把整仓变成通用审计。
- 涉及模型或工具时，检查实际送出的消息、schema、结果与诊断。文件原文不能代替执行时经过拼装、截断或默认值处理后的输入。
- 沿限制或拒绝路径追到最终执行操作，检查其他入口是否能绕过；沿状态变化追到缓存、持久化和用户可见结果。
- 测试应经过受影响的实际入口，并能捕获所述回归。检查通过、覆盖率和 Agent 自述不能代替行为证据。
- 新增抽象、配置与兼容层须有当前需求或消费者；已有设计记录提供理由，也允许被新证据推翻。

文字改动按 [maintain-prose](../maintain-prose/SKILL.md)核对语义，当前文档与行为同步。需要选择验证命令时用 [pre-delivery-checks](../pre-delivery-checks/SKILL.md)，不因审查而启动付费批次或外部发布。

只报告可说明触发条件、位置、影响和证据的问题，区分确定缺陷与待核假设。抓大放小，不用风格建议凑数量；未发现问题时说明检查范围和有影响的未验证项。收到审查意见后按技术证据修复或反驳，不默认认同。
