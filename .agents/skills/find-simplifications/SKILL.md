# 寻找有证据的简化

先确认分析还是实施，读取目标规则、架构、相关实现和设计理由。优先调查维护成本高的重复状态、重复事实、无人使用的选项，以及把同一复杂度搬到另一层的包装。

用 `rg` 查符号、配置键、事件、命令入口和动态加载，再读调用处。区分生产消费者、测试与文档引用；示例、脚本和仓外扩展可能是实际消费者，不能仅凭一次零命中判死代码。已有兼容、持久化及扩展承诺需要单独核对。

每个值得采用的候选说明：减少什么、证据是什么、保留现状最有力的理由、会失去什么，以及最小修改和验证方法。没有足够证据就保留不确定性，不凑候选数量。

检查防御代码时，区分外部输入、模型响应、持久文件及跨进程数据的真实失败，与内部重复保证同一事实的检查。多个状态或取消机制可能保护不同所有者；先追踪生命周期再合并。

考虑内置能力或依赖替换时，比较净减少的实现、测试、依赖与剩余适配成本。核查实际运行版本是否支持所需能力，不能只把维护负担移到新包装或未经验证的依赖。

实施时同步受影响的调用、测试、当前文档和生成来源，保留行为契约及有价值的失败证据。必要的局部小改直接完成；值得长期保留的理由进入已有记录，不为每项候选新建提案。

文档简化用 [maintain-prose](../maintain-prose/SKILL.md)，决策记录整理用 [maintain-decision-notes](../maintain-decision-notes/SKILL.md)，验证选择用 [pre-delivery-checks](../pre-delivery-checks/SKILL.md)。运行原件的保留按[证据规则](../../references/experiment-reports.md)判断，不能因代码可从 Git 恢复就认为随机产物可重建。
